# Taranis AI threat model

Taranis turns untrusted OSINT into intelligence products. Its two most important security decisions are **who may act on a story or report** and **which audience may receive the resulting data**. A source article may be public while its selection, analyst notes, associated reports and distribution list are sensitive.

This model covers one production deployment using the shipped ingress, frontend, Core, PostgreSQL and Redis/RQ workers. It includes optional realtime, AI and publishing integrations where they cross a trust boundary. The operator controls the host or cluster, TLS termination, secrets, backups and provider selection. Provider internals and the security of recipients' systems are outside this model. The review covers commit `59ceb31ec4a4` as of 2026-11-25.

## Data flows and trust boundaries

| Flow | What crosses the boundary | Where trust is decided |
| --- | --- | --- |
| Browser or API client → ingress → frontend or Core | Credentials, session cookies, uploads, analyst requests and exports | NGINX forwards the UI to the frontend and `/api` to Core. The frontend calls Core on the user's behalf. Core enforces API permissions. [Ingress routes](../../src/ingress/extras/default.conf.template) |
| Core → PostgreSQL and Core data volume | Users, revocations, intelligence, chat history and integration settings live in the database. The built-in publisher writes released product files to the data volume. | Database, volume and backup access can bypass application permissions. [Storage and recovery](../../deploy/README.md) |
| Core and cron → Redis/RQ → workers → Core | Job instructions, scheduling state, results and requests for worker configuration | Workers authenticate to Core with a shared service key. Queue writers and workers are privileged principals. [Worker API](../../src/core/core/api/worker.py) |
| Sources and peers ↔ collectors and connectors | Feed entries, webpages, media, tickets and intelligence exchanged with systems such as MISP | An approved source or authenticated peer can still supply hostile or misleading content. [Collector HTTP policy](../agents/http-clients.md) · [MISP synchronization](../agents/misp-auto-update.md) |
| Core or worker ↔ selected inference provider | Core sends analyst chat context. Background workers send content for their assigned AI tasks. Both consume model output. | Each provider is a data recipient with its own access and retention policy. [LLM endpoints](../agents/llm-endpoints.md) |
| Worker → publisher destination, or public reader → ingress → Core | Rendered products leave through a configured publisher or become readable at `/reports/<product-id>`. | Publishing changes the audience. The built-in link permits anonymous access. [Public product publishing](../agents/public-product-publishing.md) |
| Browser ↔ ingress ↔ Centrifugo ↔ Core | With realtime enabled, the browser receives events and may receive streamed chat text. | Core validates the connect-proxy secret and session, then assigns global, organization and user channels. [Realtime authentication](../../src/core/core/api/realtime.py) |

## Threats, controls and residual risk

Give scenarios 1–5 priority in a deployment review. Each can expose restricted intelligence or confer service-level authority across a trust boundary. The remaining scenarios cover integrity, recovery and accountability. These are design risks; their likelihood depends on the installation.

1. **Impersonation at login.** A stolen signing key, a reused bootstrap password or a misconfigured identity proxy can give an outsider an analyst or administrator identity. Production cookies use Secure and SameSite settings, cookie-authenticated writes use CSRF protection, and Core checks token revocation. Use HTTPS, unique secrets and a production authenticator. In external-header mode, the authenticating proxy must strip incoming identity and role headers, supply its own values and be the only path to login. [Authentication](../../src/core/core/managers/auth_manager.py) · [External login](../../src/core/core/api/auth.py)

2. **An analyst exceeds their clearance.** A list, export or queued action can expose records even when the detail view hides them. Core combines route permissions with object checks, including source/group ACLs and Traffic Light Protocol (TLP) clearance. A selected story export requires access to every linked source. Manual bot actions check write access before enqueue. Review wildcard ACLs and configuration roles separately. `ADMIN_OPERATIONS` bypasses content ACLs in user workflows, where role TLP checks still apply. It also grants a separate instance-wide Settings export. Check product-type readership too, since readers can retain access to an existing render after a linked report becomes restricted. [Access rules](../agents/rbac-acl.md) · [Export scope](../agents/story-export.md) · [Authorization tests](../../src/core/tests/application/mixed_flows/security/test_rbac.py)

3. **Hostile content reaches a privileged worker.** Collectors follow external links and redirects, and private sources are supported. A source can induce requests to a destination reachable from the collector, including an internal service (SSRF). Presenter templates run in a Jinja sandbox with HTML autoescaping disabled, and PDF rendering interprets the resulting HTML. Embedded markup can also survive in a downloaded HTML product, outside the preview sandbox. Restrict template authorship, worker filesystem access and outbound destinations. Allow required private feeds explicitly and isolate management and metadata services. The shipped Kubernetes network policies govern ingress only. [HTTP behavior](../agents/http-clients.md) · [Presenter](../../src/worker/worker/presenters/base_presenter.py) · [Network policies](../../deploy/kubernetes/05-network-policies.yaml)

4. **A service credential or queue writer is compromised.** A holder of the worker key can request credential-bearing configuration and submit results. A Redis writer can tamper with pending work. Core authenticates worker requests, but the key is shared and the stock ingress forwards the API prefix. Keep Redis private and authenticated, limit access to service routes to their callers where possible, and protect integration secrets in the database and backups. If the key is exposed, rotate it across its consumers and review the downstream credentials it could read. [Worker API](../../src/core/core/api/worker.py) · [Secret handling](../agents/worker-parameters.md)

5. **Intelligence reaches the wrong recipient.** A valid publish action can send the wrong render to a public URL or external destination. Core checks linked-report access for user-initiated publishing and rejects stale presenter callbacks. The built-in publisher serves a copy with sandbox and no-sniff headers. Those headers protect the browser; anyone holding the link can read the released content. Review audience, TLP, destination and automatic publishing or MISP settings before enabling delivery. Withdrawal cannot recall copies already received. [Publishing contract](../agents/public-product-publishing.md) · [Publishing tests](../../src/core/tests/application/user_workspace/publishing/test_publish_api.py)

6. **A source or model misleads an analyst, or a provider retains sensitive context.** A planted article can skew a summary or put instructions into the model's context. Chat scopes conversations to the owner, validates search filters and queries stories with the analyst's access. The chosen provider still receives prompts, recent history and selected story context. Background bots use separately resolved provider assignments. Approve each destination for the data it will receive, check retention terms and verify consequential claims against original sources before release. [Chat implementation](../../src/core/core/service/chat.py) · [Provider configuration](../agents/llm-endpoints.md)

7. **Realtime events reveal another user's activity or text.** A channel-selection error could deliver private chat text to an organization or global audience. Core derives subscriptions from the authenticated user. Chat text belongs on the owner's channel. Use distinct proxy and broker API secrets, restrict allowed origins and keep management ports private. Review the audience whenever an event gains content. [Realtime contract and tests](../agents/realtime-events.md)

8. **Work is delayed, lost or duplicated.** Slow feeds, large imports or expensive inference can starve collection and publication. NGINX limits request bodies, RSS collection caps entries and RQ enforces job deadlines. After a Redis restart, Core or cron rebuilds recurring schedules. Pending one-off jobs and delayed pushes can disappear. Monitor queue age and worker capacity. After an outage, reconcile external deliveries before retrying and restore durable records and published files together. [Queue recovery](../agents/redis-runtime-state.md) · [RSS limits](../agents/rss-source-health.md)

9. **An action cannot be attributed, or monitoring leaks information.** Core's configurable JSONL audit records capture login and human-authenticated API mutations with metadata only. GET exports and service-key actions are outside that audit trail. Restrict access to logs, set retention, and correlate job records with publisher receipts when investigating delivery. Review the destination and fields of optional telemetry before enabling export. [Audit scope](../../src/core/core/audit.py) · [Telemetry](../agents/telemetry.md)

10. **An untrusted release enters the deployment.** A compromised dependency or substituted image can inherit a service's access to secrets and intelligence. Releases provide image SBOMs and signed attestations for the production Python dependency graphs. Pin the deployed image digest, verify the corresponding attestation where available, and assess affected components when an advisory arrives. [SBOM scope](../sbom.md) · [Security policy](../../.github/SECURITY.md)

## Review and verification

Maintainers should revisit the affected flow when changing an authenticator, permission check, queued task, collector, provider, publisher, event payload or ingress route. Record the changed assumption, control and supporting test in the same change. Report suspected vulnerabilities through the [private reporting process](../../.github/SECURITY.md#reporting-a-vulnerability).

Operators can validate the model in staging with two differently cleared accounts and a synthetic report. Verify that the lower-clearance account cannot export the restricted source or queue a bot on it. Check anonymous access before and after deliberate publication. Compare the effective proxy routes, worker egress, provider assignments and backup restore scope with the boundaries above. These checks cover deployment decisions that application tests alone cannot establish.

The structure follows the [OWASP Threat Modeling Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html).
