# OSINT Source Collection Activity

Administrators can inspect recent collection activity on an OSINT source's detail page. The value appears next to the lifetime number of news items stored for that source.

Use the period control (**Day**, **Week**, **Month**) on the source's detail page to select:

- **Day**: the trailing 24 hours
- **Week**: the trailing 7 days, selected by default
- **Month**: the trailing 30 days

Changing the period does not change the lifetime total. Recent activity uses the time each news item was collected by Taranis, not the publication time supplied by the source.

## Collection updates and fuzzy grouping

Articles are identified by their sanitized URL within the same OSINT source. A repeated URL with changed title, body, author, or language updates the existing news item, preserving its ID, original collection date, analyst review, tags, and story/report membership. Story titles and analyst summaries remain unchanged. The history view shows before/after content and title differences. Unchanged normalized content and metadata create no revision.

Different URLs remain separate news items. Core compares normalized content fingerprints against the same source's items collected in the previous 30 days (UTC), selecting the strongest match at or above `COLLECTION_GROUP_THRESHOLD` (Core environment variable, default 85, valid range 1–100). An unambiguous match appends the item to the existing story; equal strongest matches in different stories produce a separate story. RT-managed stories are excluded from automatic placement and cannot receive collection updates.

A known URL is resolved regardless of its age, body length, or fuzzy score. A high score never discards a different URL's content: even score 100 can conceal a meaningful correction. No separate 95-point discard threshold is used. Without a URL, exact source/title/body repeats are skipped; changed content remains a separate item eligible for fuzzy grouping.

Core uses fuzzbite/ffuzzy CTPH scoring after NFC and whitespace normalization. Bodies shorter than 256 UTF-8 bytes have no fuzzy fingerprint, but URL-based update detection still works. RSS summaries and shared boilerplate can cause false grouping, so calibrate the grouping threshold against actual sources. Fingerprints remain internal and are recomputed on content changes.

Changed items and newly grouped items mark the story unread, refresh its collection activity timestamp, and appear in relative date windows such as Shift even when originally published earlier. Explicit publication-date filters retain their meaning. Collection sends affected story IDs to post-collection bots, including already-processed stories, and refreshes configured MISP auto-update jobs. Existing bot field-update behavior still applies; published products are not regenerated by this feature.

Core skips an incoming item only when its `published` timestamp is strictly older than the stored value. Equal timestamps still allow content updates. Accepted newer publication dates are retained, even when the content is unchanged; a date-only advance does not create a revision, change the local edit timestamp, or mark the story unread. Missing dates use the existing collector/model fallback. Different source versions with equal publication timestamps cannot be ordered and are processed as delivered. Empty replacement bodies are rejected. Results report created, updated, grouped, unchanged, and stale counts. Update-only runs are successful; unchanged/stale-only runs report `NOT_MODIFIED`. Invalid input is an error.

This applies to worker news-item ingestion. Manual items, explicit Assess creation, JSON imports, and MISP/RT synchronization retain their separate ingestion paths. Existing same-source URLs are recognized without a URL backfill; when legacy duplicates share a URL, the most recently collected item is selected and no existing item is deleted. New collection hashes are source/URL scoped; explicit title/URL identity checks also recognize collected items.

The PostgreSQL migration adds fingerprints and the story collection-activity timestamp, and backfills fingerprints only for the previous 30 days. It does not rewrite old article content or timestamps. No separate rehash command is needed. A development database that already applied this unmerged branch's migration must reapply it or be recreated using disposable data; the migration was extended in place.

Detection covers articles actually retrieved during collection. A feed returning 304, entries outside its configured limit, and articles no longer listed are not independently revisited. Feed validators apply only to the feed URL, not to linked article requests. See [Fuzzy hash use cases](fuzzy-hash-use-cases.md) for scope and the future cross-source clustering proposal.
