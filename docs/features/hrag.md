# Hybrid retrieval in Chat

HRAG combines source-backed entity/relationship evidence from Neo4j Community with semantic matches from PostgreSQL/pgvector. Chat remains the default. Each turn can select **Chat** or **HRAG** within the same conversation. HRAG answers cite graph evidence (`[G1]`) and similar passages (`[V1]`); expandable panels link to the current stories in Assess.

For a technical source walkthrough and editable draw.io diagram, see the [HRAG implementation guide](hrag-implementation-guide.md).

## Enable

HRAG requires PostgreSQL, a Neo4j database dedicated to this Taranis installation, the normal Redis/RQ worker, and cron for ongoing reconciliation. For container deployments, set `CHAT_ENABLED=true` and a strong `HRAG_NEO4J_PASSWORD`, then add `docker/compose.hrag.yml` to the normal Compose command. The overlay enables HRAG on Core/frontend, adds Neo4j, and uses the pgvector PostgreSQL 18 image. It adds two extraction workers (`HRAG_EXTRACTION_WORKERS`, default 2) and one dedicated embedding worker to bound extraction concurrency and reserve embedding capacity. Provider rate limits and article length still determine elapsed indexing time. Verify that the existing PostgreSQL major version matches before switching images; follow the normal PostgreSQL upgrade process otherwise. Do not reuse a database volume across major versions.

For host development, use `dev/compose.hrag.yml` with `dev/compose.yml`, set `CHAT_ENABLED=true` and `HRAG_ENABLED=true` on Core/frontend, and set Core's `HRAG_NEO4J_URI=bolt://127.0.0.1:7687`, `HRAG_NEO4J_USER=neo4j`, and `HRAG_NEO4J_PASSWORD`. Enable the existing cron process (`WITH_CRON_RQ=1`). Host workers include `Embeddings` and `HRAG` in their default worker types; include these roles in explicit `WORKER_TYPES` overrides or run dedicated workers for them. The overlays keep the default deployment unchanged.

Core creates new indexing tables and runs `CREATE EXTENSION IF NOT EXISTS vector` when enabled. A database administrator may install the extension first if Core's database role lacks that privilege. Neo4j credentials need schema/index creation and read/write access; the graph database is selected with `HRAG_NEO4J_DATABASE` (default `neo4j`). Core alone connects to either database. Keep Bolt private; use `neo4j+s://` for verified TLS when connecting across untrusted networks.

In **Admin Settings > LLM Endpoints**, enable an **Embeddings** format on an OpenAI-compatible endpoint. Assign **HRAG embeddings**, **HRAG entity and relationship extraction**, **HRAG relationship verification** (Decisions), and **HRAG graph planning**. These require realtime processing in v1. In **Settings > Chat**, extraction reasoning defaults to **Low** for initial proposals; select a supported effort or **Provider default** if the extraction model rejects it. Other features keep their existing reasoning behavior. Saving the assignment/effort queues a synthetic endpoint check using that effort. Chat's existing endpoint synthesizes and streams answers. Set `HRAG_EMBEDDING_DIMENSIONS` to a dimension supported by the embedding model (default 1536). Indexing and query requests explicitly send this dimension and reject mismatched output. With HRAG enabled, embedding endpoint health checks request and verify the same configured dimension; unsupported dimensions fail the check. Provider changes create a separate generation; do not silently replace the model behind an unchanged model identifier.

Core and worker pin `taranis-llm-bot==0.1.8` from PyPI. They use llm-bot’s embedding client and prepared extraction, graph-query generation and final HRAG tasks. Core and Worker supply their existing HTTP transports for embeddings; llm-bot builds requests and validates vectors and dimensions. Chunking, scheduling, storage and similarity search remain in Taranis. Sentiment now requires a realtime Decisions endpoint; assign **Sentiment analysis** or a compatible bot override before running it. Core installs the transport-free library; workers install its `inference` extra. This avoids mixing Requests and Niquests transport packages in Core.

## Inputs and indexing

Only NewsItem **content** is sent for indexing. Extraction uses the first 20,000 Unicode characters (`HRAG_EXTRACTION_LIMIT`). Semantic indexing uses the runtime character limit (initially `HRAG_EMBEDDING_LIMIT`, default 10,000) and splits bounded content at paragraph/sentence boundaries, defaulting to 2,000-character chunks with 200-character overlap. The limits are independent. Title, review, tags, and regrouping do not trigger inference. Content edits beyond the relevant cutoff reuse that pipeline's result. Empty content needs no inference. Panels identify truncated items.

**Administration > Settings > Chat > HRAG semantic search** controls chunking, size, overlap and indexed characters. Overlap must be less than half the chunk size. Saving indexing settings queues reconciliation and builds a separate embedding generation. Increasing or decreasing size rebuilds from NewsItem content; **Activate** switches to a ready replacement while the existing index remains searchable. Disabling chunking embeds one bounded passage per item. Chunk offsets and vectors save atomically with work status; citations reconstruct the matched source passage. Retrieval caps (default 12 chunks, at most 3 per NewsItem) apply immediately without reindexing. Character limits are distinct from embedding-model token limits.

The fixed v1 vocabulary preserves existing NER types and adds vulnerability, campaign, incident, mitigation, location, infrastructure, motivation and capability. Extraction schema v5 uses the shared llm-bot entity/relationship extraction task with Taranis’s output schema and source validator. It uses a generative LLM to propose entities and relationships with required assertion polarity. Taranis computes exact Unicode offsets locally; repeated names/quotes use the first exact occurrence. Invalid entity evidence triggers the existing repair attempt; malformed relationship evidence or incompatible endpoints are quarantined individually.

A realtime Decisions endpoint then verifies each valid proposed relationship against its source passage, including sentence context. It chooses affirmed, negated, uncertain or not stated. Only assertions with probability at least 0.8 survive; verification can correct polarity but cannot invent edges. Verification failure retries the item without publishing an unverified graph. This favors precision over recall: missing entities/relationships are accepted, and semantic retrieval remains independently available. Only the final verified result is cached for graph recovery. A Decisions endpoint is required even when the proposer returns no relationships.

Only validated CVE identifiers merge across articles in v1. Names remain separate, and aliases cannot establish multi-hop factual paths. Extraction exposes a deterministic compatible NER-tag projection; standalone NER remains available. HRAG indexing does not invoke a second NER task.

PostgreSQL stores generation configuration, fingerprints, leases, retries, extraction output, and vectors. Redis executes work; it is not the index ledger. Startup queues reconciliation, and cron repeats it every minute. Each pass scans up to 500 items per generation and queues up to 50 jobs per pipeline. Embeddings use the `embeddings` queue and extraction uses `hrag`, with independent dispatch allowances. A lost queued/running job becomes eligible after its 15-minute durable lease. Failed jobs use bounded exponential backoff up to one hour. Repeated callbacks are idempotent; outdated fingerprints and lease tokens are rejected. Missing Neo4j projections rebuild from saved extraction output without another inference call. Deletions cascade in PostgreSQL; reconciliation prunes graph assertions and unused entities.

In **Administration > Settings > Chat**, use **Start indexing** to queue a backfill pass and **Refresh status** to inspect ready, running, queued and pending work for each generation. This works without cron; continuous indexing and retries still require the cron process.

Administrators can also use the authenticated API:

- `GET /api/settings/hrag`: generations and work counts.
- `POST /api/settings/hrag` with `{"action":"backfill"}`: queue reconciliation now.
- `POST /api/settings/hrag` with `{"action":"activate","generation_id":"…"}`: activate a completed generation, after rechecking all current inputs.
- `POST /api/settings/hrag` with `{"action":"reprocess","generation_id":"…"}`: invalidate and rerun that generation. This incurs inference again.

The first generation of each pipeline becomes active during its initial backfill. New model, verifier, extraction effort, input-limit, chunking or schema configurations build alongside the active generation and require explicit activation. Old generations remain stored. Credentials can rotate without changing the generation; the proposer/verifier model, format, destination and extraction effort are frozen. Existing v2 graphs remain readable until a verified v5 generation is activated; old generations without a verifier do not accept new extraction work. Use a new model identifier or schema version when replacing model weights in place.

## Retrieval and permissions

Chat resolves and validates Assess filters using its existing `search_stories` call and search helpers. The llm-bot graph-query task separately returns only entity names/types, relationship types and hop count, validated through Core’s `GraphPlan`. The graph planner receives no filter catalog or filter metadata. Core selects fixed parameterized Cypher; model-generated SQL/Cypher is never executed. Default limits are three relationships, 50 graph evidence rows and 12 vector matches (`HRAG_GRAPH_LIMIT` and `HRAG_VECTOR_LIMIT`). Multi-hop paths use affirmed assertions only. Both branches apply the same Chat-resolved filters. If graph planning fails, vector matching retains those filters. Invalid or missing Chat filter resolution fails the turn before either retrieval branch runs.

Current source ACLs, story and NewsItem TLP, active generations and content fingerprints determine eligible assertions before traversal output, ranking and limits. Every supporting assertion in a path must pass. Core rechecks before synthesis and display, and resolves current story membership. Saved messages retain references, not copied passages. Answers whose evidence or inherited conversation evidence becomes inaccessible are withheld on reload and from later provider context.

Vector retrieval currently uses exact cosine ranking over authorized items. This preserves correct filtered top-k results and supports mixed stored dimensions across separate generations; a future ANN optimization must preserve that authorization behavior. Corpus scans and authorized-key lists favor straightforward correctness in v1; measure larger deployments before assuming benchmark timings apply to application queries.

The final llm-bot HRAG task returns a structured answer, citations and an insufficient-evidence flag. Core decodes only the answer field for streaming, including escaped text, and validates the full response and citation IDs before saving. Invalid output gets the library’s one repair attempt within the same turn deadline. Saved extraction reasoning choices remain unchanged; select **Low** explicitly when replacing an older **None** setting.

One retrieval failure yields a partial answer and a notice. Two failures leave the turn unsaved. Successful empty retrieval reports insufficient evidence. Counts are explicitly limited to indexed, accessible, retrieved evidence and cannot be treated as complete corpus counts.

## Backup and recovery

Back up PostgreSQL with its normal procedures, including HRAG tables, settings and pgvector. Neo4j is a rebuildable projection. After restoring PostgreSQL into a compatible pgvector-enabled database, an empty Neo4j instance can be rebuilt by reconciliation; embedding vectors remain in PostgreSQL. For a Neo4j Community dump, stop the database/DBMS as required by the installed Neo4j version; do not assume Enterprise online backup is available. Validate restores in an isolated environment before relying on them.

Disabling `HRAG_ENABLED` stops indexing and new HRAG turns while preserving PostgreSQL data and Chat history. Existing history still rechecks evidence permissions. The scoped integration/browser checks use disposable Neo4j and pgvector services and a scripted provider; they establish workflow correctness, not the factual quality of a chosen extraction or embedding model.

## Model quality evaluation

The selected private corpus remains at `taranis_data/hrag/sample.json` (120 items from 33 sources). Once extraction and embedding endpoints are selected, run `dev/evaluate_hrag.py` in the worker environment with `--sample`, `--endpoints`, `--dimensions`, and `--output`. The endpoint file contains `extraction` and `embedding` endpoint objects, including credentials if needed; keep it outside Git. Write output under ignored `taranis_data/hrag/`. Metrics count schema/passage-valid outputs, truncation, entities and relationships. The private annotation JSONL keeps source references, existing NER tags and review fields for assessing correctness and missed assertions. Existing tags and automatically valid quotes do not establish semantic correctness.
