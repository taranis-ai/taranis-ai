# Assess Filters

## When To Load

Assess sidebar/search/default filters, `/assess`, `/api/assess/filter-lists`, asset matching and evidence, omnisearch filter syntax, or pagination.

## Contracts

- Assess removes empty GET parameter values before rendering. Native navigation redirects to the clean Assess URL; HTMX normalizes request arguments in place and returns `HX-Push-Url` so filters stay asynchronous. Preserve repeated non-empty values and explicit values such as `false` and `0`.
- Without JavaScript, search and the native sidebar filters submit through one GET form, and the form exposes an explicit Apply filters button. Source, language, group, and tag filters are hidden because their token-selection workflows require JavaScript.
- Filter lists contain at most 1,000 current user-visible options per list, ordered by name (normalized value for languages). Core applies the limit in SQL after visibility filtering. Tags start from distinct non-report names in `NewsItemTagCluster`, then probe indexed tag occurrences for a non-report tag on an ACL/TLP-visible story. Deduplicate candidates before these checks; `OFFSET 0` keeps PostgreSQL from expanding the probes into a full tag-table join. Core builds lists on request; frontend caches per user. Writes affecting those options must invalidate the relevant frontend scope. Chat's reference catalog omits options beyond this cap; direct Assess filters still accept them.
- Assess tag suggestions use `/api/assess/taglist` directly, independently of the filter-list cap/cache. Search matches literal substrings case-insensitively after trimming whitespace. Rank exact names first, then distinct ACL/TLP-visible story counts descending, then case-insensitive name and original name for stable ties; apply pagination afterward (20 suggestions by default). Combine occurrences across tag types, exclude types with a literal `report_` prefix (case-insensitive), and count each story once. Types such as `reporting` remain eligible. Frontend forwards the search as an encoded query parameter.
- Tag suggestions return `{name, story_count}` objects; the displayed count reuses the ranking aggregate without extra queries. Counts cover all visible stories bearing that tag, independently of other active sidebar filters. Rows truncate long names to one line, preserve the full name in the button title, and keep the count visible. The Assess browser workflow checks long URLs and names with spaces for truncation and row overlap.
- The remote token control's HTMX request guard reads `this.value`; HTMX inline handlers cannot call Alpine component methods such as `hasQuery()` directly. The Assess browser workflow covers searching and selecting a tag.
- Assess, Chat, and source/group references share `FilterData`, limited to ACL/TLP-visible stories. Sources/groups without visible stories are omitted; reference ACLs still apply.
- Story filters use existence checks for source/language membership, tags, reports, and attributes so matching related rows do not multiply stories. Source/group alternatives and language constraints must match the same news item. ACL and TLP checks remain on the filtered story query.
- Asset matching requires both `ASSESS_ACCESS` and `ASSETS_ACCESS`. `AssessSearchFilters` includes `asset_match`, `asset_id`, `asset_group_id`, normalized `asset_tag`, independent `asset_cve_match`/`asset_software_match` (`any|yes|no`), and optional inclusive `asset_cvss_min`/`asset_cvss_max` (finite 0–10, ordered). An active advanced field enables matching. Turning off the checkbox clears advanced fields while preserving ordinary criteria, including tags; a form marker makes native submissions behave the same way. Advanced controls expand when active.
- `core/service/assess_asset_matches.py` supplies one qualification path for story selection, counts, `matched_assets` summaries and expanded evidence. Scope, match choices and scores must hold on the same article/asset association; the two match types may concern different installed components. Contradictory choices return no matches. Candidate stories follow Assess's ordinary filters and stable sorting, before pagination.
- In asset mode, full normalized CVE tag identifiers match enabled imported findings exactly, never by substring. Multiple selected CVEs require the same asset to cover every identifier across qualifying articles in the story. Only qualifying assets contribute to evidence/counts. Ordinary tag semantics remain unchanged outside asset mode and for non-CVE tags.
- CVSS uses the highest valid source-reported score for each article/asset association, restricted to selected CVEs when present. Missing scores fail either active bound; zero is valid. Preserve source, vector and exact source-record component references. Assess publication/time filters keep their existing semantics; package/PURL, collection dates and score availability are deferred.
- Cards lead with `matched_assets` summaries: asset identity, highest reported CVSS, distinct matching CVE count and software-match presence across qualifying articles. Repeated CVEs count once per asset/story. Severity uses green for CVSS below 4, yellow for 4–6.9 and red for 7–10, with text labels; missing scores remain gray/unscored, distinct from zero. These summarize relevance and source-reported severity, not confirmed exposure. **Why this matches** loads `/api/assess/stories/{story_id}/asset-matches` on demand with a native full-page fallback. Evidence groups articles by ID and assets within each article; installed versions, rating provenance and excerpts remain collapsed until opened. Asset links preserve Back to Assess context.
- `/api/assess/asset-filter-lists` reads accessible assets, groups and classification tags. Catalogs, matching lists and evidence bypass frontend caches, recheck organization/default-group access, story/source ACLs, article TLP and current rules/findings, and return static failures. Successful story actions refresh the filtered list; failures preserve it. Matching streams bounded candidate/count batches, retaining page summaries; `no_count` stops once the page is full.
- Single-asset Assess reads the requesting user's latest scan status before fetching stories, polls results while queued/running and includes the completed results in the final refresh. Historical scan controls live in Matching rules. Shared filters survive defaults/saved filters, paging, infinite scroll, actions, and native return navigation. Coverage extends existing SBOM and Assess workflows.
- Bulk updates own one transaction: missing, forbidden, or failed stories roll back every change, revision, and asset-evidence refresh. Model `Story.apply_update` does not commit; the single-update wrapper retains its commit. Scheduling, cache invalidation, and realtime publication run only after the bulk commit. Error responses preserve the visible list and selection.
- Assess selection is initialized by the stable `assessSelection` expression in `assess-navigation.js`; changing inline `x-data` attributes during HTMX settling can initialize nested scopes twice. Card initialization and local swap events refresh metadata; no subtree observer is needed. Pagination returns only the list/pagination fragments. Active-filter chips also request an out-of-band sidebar replacement to keep native inputs consistent.
- Display preferences (compact view, search highlighting, and bookmark bar visibility) use `/assess/display`, preserve the current filters/selection, and update the request's current-user profile before rendering. Invalid preferences return HTTP 400 through the shared validation formatter. Failed saves notify and retain the list; explicit local HTTP 400 targets are required because the shared body validation rule otherwise overrides the broader 4xx rule. Headline links open stories; checkboxes select them. Custom dates and advanced criteria remain expanded when active.
- Paged user lists select ordered story IDs before loading story content and enriching votes/report counts. Every sort ends with the story ID as a stable tie-breaker. Counters project only ID/read/important, remove ordering/paging, and aggregate the filtered set once; `in_reports_count` retains its report-association count semantics.
- Story views reuse filter lists by user within the current request even with `CACHE_ENABLED=false`. This includes repeated detail/form context construction; subsequent requests still fetch fresh lists when the frontend cache is disabled.
- Failed upstream list loads return a static message and HTTP 502. HTMX receives a notification-only fragment; native navigation renders the Assess page with the error. Filters, bulk status actions, and story deletion route 5xx responses to the notification bar without replacing the visible list. Delete/Ungroup preserve Core rejection statuses and route 400/4xx/5xx responses to notifications. Failed sidebar requests suppress history pushes; failed Any time requests restore time controls from the unchanged current URL so the reset can be retried. Return only the load error even after a successful action; HTMX selects the first notification bar. Never expose exception text.
- Story/report writes also invalidate news-item, bookmark, and filter caches. Admin ACL/role/source/group/settings writes invalidate all frontend caches.
- Bulk story updates reject non-string story IDs with a static 400 before looking up or updating any story. API coverage is in `test_assess_api.py`.
- Sidebar submissions, profile defaults, and dashboard shortcuts share canonical query parameters; source/group/language/tag values remain list-shaped. Saving an existing filter name updates it; identical criteria under a different name are rejected after canonical validation and serialization, including case normalization of choice fields.
- The sidebar's Save & manage searches control opens saved-filter management, where users can create filters from the current criteria, apply saved filters, set defaults, and delete filters. Sort labels and help distinguish the publication-derived story date from update time; relevance uses story score with full-text search rank taking precedence when applicable.
- List refreshes after non-GET actions restore the active query from `HX-Current-URL`, including DELETE story actions. Deleting the last matching story leaves the filtered result empty; it must not show unfiltered stories while the sidebar still displays active filters.
- Story cards keep tags matching any active tag-name or tag-type filter visible and highlighted even when collapsed or compact. Card/list replacements after mutations recover active tags from the Assess `HX-Current-URL`, including HTMX PUT actions. Tag expansion is local to the tag list; opening story details shows all tags without the former twenty-tag cap. Coverage belongs to the Assess browser workflow and story view tests.
- Source icons on story cards add that source through a native Assess link, preserving repeated filter values and existing sources while clearing pagination. Assess list GETs use the requested filters, since `HX-Current-URL` still describes the previous search during an HTMX filter change. Card replacements and detail returns retain the Assess filter context.
- Dashboard shortcuts reuse saved-filter normalization, delete routes, and Assess URLs. Show the first three by default, with the rest behind Show more.
- Omnisearch fetches filter lists lazily, only for value resolution/suggestions.
- Paged navigation replaces `#story-list` and out-of-band `#story-pagination`, scrolls to the top, and keeps the sticky top bar mounted. Errors notify without replacing/appending stories. Stable search-input IDs preserve focus.
- Story Open/Edit, matched-asset links, and the selection shortcut carry a relative `assess_url`. Editors preserve it through layouts, saves, and card replacements; asset pages preserve it through inventory/findings/rules navigation, filtering, replacement previews and scan redirects. Explicit return URLs take precedence over `HX-Current-URL`, which stays on the initial page during infinite scroll. Back to Assess restores filters and pagination with a native link; only the application's Assess path is accepted. Direct story links fall back to ordinary Assess, and bookmark returns keep their existing destination.
- Selection Edit captures its component root during initialization: Alpine's `$el` points at the triggering button in action handlers. The real Assess browser workflow covers Shift+E and toolbar Edit navigation and the return search; do not stub `openStoryEdit` in shortcut coverage.
- Assess remembers the latest search in user- and application-path-scoped localStorage. Opening bare Assess offers Restore last search or Dismiss; explicit filters, saved defaults, and reset links take precedence. Pagination updates the stored URL. Storage failures do not affect native return navigation.
- Infinite-scroll searches opened past the first page explain their starting result and offer Start from beginning with the same filters. Counts label the stories actually loaded; the footer range includes all appended batches and End of results does not imply earlier results were loaded.
- `Shift+Space` prevents native page-up on keydown and performs read/unread on keyup only with a selection. Bookmark detail shares this behavior and the [global shortcut/selection rules](frontend-development.md).
- Successful clustering replaces the saved Assess selection with the first story in the submitted dialog order before the list swap; merged-away IDs must not survive into the next action. Failed clustering preserves selection and the open dialog. `test_user_assess` in `test_e2e_user.py` requires three cards and performs two merges, checking the surviving selection and removal of each secondary card.
- The shared Assess/bookmark selection toolbar keeps action positions stable between one and multiple selected stories. Counts and actions wrap when the toolbar cannot fit, keeping Clear selection reachable. The single-story cluster hint uses only spare space and disappears when it cannot fit.
- The Assess pagination/editing browser workflow reads the stored source ID from its seeded story and filters to that source so scheduled collection from other sources cannot change its expected total.
- Browser tests use `_get_assess_story_counts` to wait for both Alpine counts; wrapper visibility is insufficient.
- Search submits after a 300 ms input debounce; blur does not submit again. Filter and pagination requests share the sidebar replacement queue so newer criteria cancel older in-flight requests. Browser tests wait for the input request before continuing; blur has no HTMX wait. The Assess workflow injects a display-save HTTP 400 to verify list/selection recovery; its expected network-console message is allowed only for that workflow and endpoint.
- `AssessSearchFilters` owns filter validation and serialization for Core, saved filters, and Chat; paging/internal controls stay separate. Chat links use canonical `/assess` queries with doseq encoding.
- Advanced asset fields are omitted from Chat’s tool schema and rejected if a provider submits them until asset-reference validation is supported. Omnisearch syntax is unchanged.
- Before `Story.get_by_filter(filter_args, current_user)`, Core validates model-proposed source, group, tag, language, and recent-story references against the user's visible catalog. Chat must never bypass this validation or turn proposed filters into raw SQL.

Relative date windows and explicit `timefrom` use the publication-derived story `created` date. Collection changes mark stories unread but do not force old stories into the current Shift window. See [Collection Updates](fuzzy-deduplication.md).

The Time period dropdown preserves canonical range values and unlisted saved `last<N>` ranges. `shift` starts today at 00:00 UTC, `week` starts Monday at 00:00 UTC, and `month` starts on the first at 00:00 UTC. `24h` and `last<N>` count back from the current UTC time, not midnight. Legacy `day` starts yesterday at 00:00 UTC. Custom bounds remain additive (`timefrom` on story creation date, `timeto` on last update); Selecting Any time removes the preset and both bounds without dropping other criteria. Custom-only bounds select a disabled Custom dates placeholder so Any time remains an explicit selectable reset; no UI-only range value is sent to Core. Boundary coverage is in `test_time_period_boundaries`.
