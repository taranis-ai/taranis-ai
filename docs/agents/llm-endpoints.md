# LLM Endpoints

## When To Load

Shared LLM settings, provider assignments, Chat configuration, clustering, summary/title, NER, sentiment, or classification execution.

## Contracts

- Admin Settings always shows LLM Endpoints, independently of `CHAT_ENABLED`. Each named endpoint stores base URL, model, API format, API key, and positive timeout in the singleton settings JSON. No new tables or migration are required.
- A bot’s `LLM_ENDPOINT` selection wins over its feature assignment; explicit feature assignments win over the shared default. An empty assignment inherits the default; an empty default leaves unassigned features unconfigured. Titles use the summarization assignment. NER, sentiment, and cybersecurity classification use `ner`, `sentiment`, and `classification` feature assignments and the same internal library/client as clustering and summary.
- Endpoint mutations and assignments lock the singleton settings row. Delete returns 404 for a missing or unknown endpoint ID and refuses endpoints used by a default, feature assignment, or any bot (including disabled bots). Bot selection validation shares the settings-row lock with deletion. Settings PATCH cannot bypass endpoint validation by replacing the endpoint dictionary. Endpoint names are unique ignoring case.
- Settings responses omit endpoint API keys and expose only `api_key_configured`. Blank retains an existing key; explicit clear removes it. Keys remain in the database, so protect database access/backups. Admin mutations require `ADMIN_OPERATIONS` and return JSON; `/worker/bots` and `/worker/bots/<id>` require the service API key and send `Cache-Control: no-store`; only these bot responses include the resolved `llm_endpoint` with raw credentials.
- Deployment `DEFAULT_LLM_ENDPOINT` is a JSON endpoint object, disabled by `{}` or when unset. `Settings.initialize()` registers it on fresh databases and upgrades only if the shared default is empty; a saved endpoint with the same base URL is reused without changing any provider fields. Existing defaults and feature/bot assignments win. Shipped deployment stacks use private Gemma CPU inference (`llm-inference:8000/v1`, Chat Completions); development uses loopback. The published CPU image supports amd64 and arm64; deployment manifests leave architecture selection to the runtime. Clearing a default while this bootstrap is configured reselects it on restart. No standalone NLP HTTP services are required.
- Old `chat_llm_*` values convert to `existing-chat`, assigned only to Chat. This avoids changing destinations for background content without an administrator choosing a default. Conversion persists during initialization or the next settings write.
- Core reads settings each Chat turn. Core includes the effective endpoint in the bot configuration fetched once per run; workers make no separate endpoint lookup and pass all provider values explicitly to the internal library; no worker `LLM_*` fallback, including when model is empty. `REQUESTS_TIMEOUT`, when set on a bot, overrides the endpoint timeout. A running job keeps its starting configuration.
- Provider errors retain retryable `bot_service_unavailable`; task errors remain static and suppress exception chains. Invalid summary/title output fails the job rather than skipping stories and reporting success. Missing configuration persists a non-retryable `llm_not_configured` result directing the administrator to LLM Endpoints. NER returns entity tags with story cybersecurity mode. Sentiment stores validated category/score attributes. Classification honors the bot threshold and keeps item scores and aggregate story status; empty item content is skipped. Invalid provider output fails instead of silently skipping it. Clustering keeps its reduced story payload. Summarization uses the library's summary/title schemas and prompts, updates a title only for multiple news items, and marks successful updates through the existing story attribute workflow.

## Entry Points and Coverage

- Shared validation: `src/models/models/llm.py`; persistence and resolution: `src/core/core/model/settings.py`.
- Admin/worker boundaries: `src/core/core/api/settings.py`, `src/core/core/api/worker.py`; frontend: settings view and `settings/llm.html`.
- Worker client/error boundary: `src/worker/worker/llm.py`; all five LLM bots.
- `src/core/tests/test_settings.py` covers deployment default initialization, reuse, preserved edits/assignments, external defaults, and disabling bootstrap.
- Extend the admin API settings workflow for resolution, secrets, and deletion; the Chat client suite for both API formats; worker bot workflows for real library prompts/parsers; and `test_admin_settings` for create, validation recovery, assignment, reload, preserved keys, and deletion guards.

## Endpoint checks

- Saving an endpoint queues a small synthetic inference through the existing RQ worker; Core startup checks every saved LLM endpoint. All LLM bots use the health of their selected endpoint or inherited assignment; legacy unused URLs are not probed.
- Checks validate an actual Responses, Chat Completions, response, including authentication/model selection. Synthetic requests contain no stories but may incur provider usage. Failed checks retry through RQ after 10, 30, 120, and 300 seconds; worker scheduling can delay those intervals. After exhaustion, save the endpoint/bot or restart Core to recheck.
- Redis owns check state separately from task history. Pending or failed checks taint `/health` (`worker_endpoints=down`, HTTP 503); checks are `n/a` with queues disabled. The container `taranis-core-healthcheck` still requires database/seed/broker/worker health but tolerates endpoint-only degradation, keeping Core reachable for configuration repairs and retry results. Unassigned saved endpoints are checked too. Disabled bots do not contribute bot status; every saved endpoint is checked even when unused. Deleted endpoints do not taint health.
- Each check carries a generation and configuration fingerprint; edits/deletion discard obsolete results. Worker-only configuration responses are non-cacheable. Public status uses static messages and contains no credentials or provider error text. Completion invalidates settings, bots, menu badges, and dashboard/health caches.
- The bot overview shows one current status: disabled first, then failed/pending endpoint checks, otherwise the last execution status. Execution history stays in the detail page. Failed checks join the bot failure filter/menu count; healthy checks clear only the endpoint failure. LLM settings retain their endpoint-health badges.
- Entry points: `core/service/endpoint_health.py`, `worker/endpoint_health.py`, and `/worker/endpoint-health/<kind>/<id>`. Coverage extends the health API lifecycle, worker probe cases, settings browser workflow, and full-stack RQ tests.
