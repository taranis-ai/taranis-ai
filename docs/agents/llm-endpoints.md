# LLM Endpoints

## When To Load

Shared provider settings, Chat configuration, LLM bot execution, or endpoint health checks.

## Contracts

- **Admin Settings > LLM Endpoints** is available independently of `CHAT_ENABLED`. Named endpoints share enabled state, provider base URL, processing mode, API key, and positive timeout. `api_formats` maps each enabled format to its model and optional base URL override; at least one is required. Existing single-format settings normalize without changing assignments or models; legacy API-format edits retain the current model unless a replacement is supplied. Names are unique ignoring case. Processing defaults to realtime. One endpoint can serve Responses, Chat Completions, and Decisions simultaneously. Topic classification selects `systemone`, then `openai_decisions`; other features prefer Responses, then Chat Completions. Each uses its own model and URL. Decisions uses realtime processing even when other formats use batch. Its URL defaults to `/systemone` or `/decisions` under the provider base URL; full URL overrides are used as supplied without appending a format suffix. OpenRouter requires a batch-capable model at submission. Base URLs exclude `/batches` as well as inference paths.
- The endpoint form has one Decisions card with one enabled flag, API format selector, and model. Its System One and OpenAI choices use a manual URL override; the OpenRouter choice hides/disables that field and maps to `systemone` with `https://openrouter.ai/api/alpha/decisions` automatically, without adding an API format to Core. Saved System One configurations with that exact URL render as OpenRouter; switching away exposes a blank override rather than reusing the hosted URL. The form opens with the effective saved protocol (`systemone` before `openai_decisions`); saving submits only the selected Decisions format through the existing `api_formats` contract. Mapping native `decisions` fields before filtering preserves the submitted selection, model, URL, and unchecked enabled state on validation errors. The existing admin settings browser workflow covers OpenRouter persistence, switching protocols, and validation-error preservation.
- Disabled endpoints are unavailable to Chat and block bot dispatch, cron registration, collector chains, and dependent pipelines without changing each bot's saved enabled flag. Assignment/state edits immediately refresh registrations; enabling schedules eligible bots and queues a new probe. Development (`DEBUG=true`) defaults new/missing endpoint states to disabled; production defaults to enabled. Explicit saved states survive restarts. Workers reject disabled configurations; jobs already running or checkpointed keep their starting configuration. Disabled assignments do not fall back to another provider.
- Resolution order: bot `LLM_ENDPOINT`, feature assignment, shared default. Blank inherits; no default leaves unassigned features unconfigured. Titles share the summarization assignment. Core resolves Chat each turn and includes the effective provider in bot configuration once per run. Running jobs keep their starting provider configuration.
- Explicit feature/bot assignments require a compatible enabled format. Endpoint edits reject losing previously supported formats still needed by those assignments. Stale classifier assignments retained during an upgrade do not block provider maintenance such as disabling it or rotating its key. Existing configurations and shared-default inheritance remain loadable during upgrades; classification still requires a Decisions endpoint before execution.
- Network timeout overrides and execution budgets follow [Worker Parameters](worker-parameters.md).
- Endpoint and assignment mutations lock the settings row. Deletion rejects default, feature, or bot references, including disabled bots; unknown IDs return 404. Bot selection shares the lock. Settings PATCH cannot replace the endpoint dictionary to bypass validation.
- Admin mutations require `ADMIN_OPERATIONS`. Human responses omit API keys and expose `api_key_configured`; blank preserves a key, explicit clear removes it. Only authenticated worker bot/configuration responses include raw credentials and use `Cache-Control: no-store`. Protect database access and backups.
- HTTP is supported for administrator-selected deployment networks. It sends credentials and content without encryption, including automatic checks of unassigned providers. Use HTTPS across untrusted networks.
- The seed manager's `pre_seed_llm_endpoints()` runs from fresh seeding and `pre_seed_update()` after settings initialization. It ensures an endpoint at `http://llm-inference:8000/v1`, reusing one with that URL. New endpoints use Chat Completions and a blank model for the provider default. Startup refreshes its secret from `LLM_INFERENCE_API_KEY` (blank clears it), preserves saved enabled/model/API/timeout values and assignments, and selects it only when the shared default is empty. Deleting it causes recreation on restart. `Settings.initialize()` owns settings persistence, without invoking seed migrations. Deployment and rollback: [upgrade notes](../../deploy/README.md#shared-llm-endpoint-upgrade).
- Existing Chat provider settings become a Chat-only endpoint, preserving the destination without assigning background content to it. Conversion persists at initialization or the next settings write. Bot parameter compatibility belongs in [Worker Parameters](worker-parameters.md).
- Workers pass provider values explicitly to `taranis-llm-bot`; there is no environment fallback. Transport errors use retryable `bot_service_unavailable`; request timeouts use retryable `llm_request_timeout`; invalid output uses `llm_invalid_output`; missing configuration uses `llm_not_configured`. RQ deadlines propagate as retryable `job_timeout` with execution-budget guidance. Public errors are curated; exception details stay in logs.
- NER enables cybersecurity mode for stories classified as security incident, vulnerability, threat intelligence, security policy, or security news; sentiment stores validated category/score attributes. General classification uses the eight llm-bot categories, stores each item’s highest-scoring `classification` and JSON `classification_scores`, and derives the story’s most common category (ties follow library category order). Empty content makes no inference and clears old topic results. Core recomputes the category after item edits/grouping; no classified items yields `none`, displayed as Not Classified. The old binary threshold is accepted for stored configurations but hidden and unused. Disinformation describes the subject of coverage, not a truth verdict. Summary/title updates use library schemas/prompts and change titles only for multiple news items. Core records each stage's completion attributes after committing its results, including successful empty findings. See [Bot Run Order DAG](bot-run-order-dag.md) for scoped selection and [Story Clustering](story-clustering.md) for its reduced input.
- NER shares the immediate tag-save path with wordlist, IOC, and regex tagging, uploading each nonempty item result through `PUT /worker/tags?replace=false` before its next inference. Prior uploads survive later failures; empty findings need no upload. An unsuccessful response, including HTTP 207 with item errors, stops the run with `tag_save_failed`. Tag writes advance the shared expected story revision once each, preserving the final submission's stale-edit check. Uploads and expected revisions are checkpointed so timeout continuation skips saved items. Completion attributes still require a successful final submission. Batch NER validates the complete batch before uploading its items.

## OpenRouter batch processing

- Select **OpenRouter batch**, `https://openrouter.ai/api/v1`, either supported API format, and a batch-capable model (including `:batch` slugs). Workers submit inline requests to `/batches` with the API shape and model before the requests array, then retrieve inline results by batch ID. No JSONL upload is needed. The worker uses the prepared-task API from the published `taranis-llm-bot==0.1.6` package: `build_request()` constructs provider payloads and `parse_result()` validates returned bodies. Taranis owns submission, polling, and RQ state. Protocol: [OpenRouter quickstart](https://openrouter.ai/docs/batch-quickstart).
- Chat assignments, including inherited defaults, must resolve to realtime. Settings reject assignment or endpoint edits that would make Chat use batch, even while Chat is disabled. To use a batch default, assign Chat an explicit realtime endpoint first.
- One RQ bot job snapshots its configuration and selected stories in private Redis job metadata. Requests share a batch per output schema; separate schemas support Google's batch constraint. Each selected input has its own positional `custom_id`, including identical content. Bots first prepare the complete list of requests, then choose batch submission or sequential immediate execution. All batch results are correlated and parsed through the library before applying updates; invalid batch output fails without issuing repair requests. Immediate execution retains the library repair attempt. Clustering compares the full story list in one request in either mode.
- The same job returns RQ `Retry` at five-minute intervals until results arrive, keeping dependents deferred and avoiding a worker occupied for the provider's 24-hour window. Provider wait is separate from the per-attempt RQ execution deadline. Transport failures while polling retry; rejected polling requests, missing/duplicate/failed results, and terminal provider failures produce curated failure results. Each submitted batch has a 25-hour retrieval deadline, including scheduling grace. No success history is written at submission.
- Standalone jobs submit staged changes with expected story revisions, advanced by their NER tag writes. DAG pipelines checkpoint the shared context and completed stages, resume each pending batch, and submit every stage in one transaction after completion; see [Bot Run Order DAG](bot-run-order-dag.md).
- Redis contains credentials/content while the job is pending; successful completion removes its snapshot. Worker restarts resume from metadata, but Redis restart loses pending jobs per [Redis Runtime State](redis-runtime-state.md). A submission with a lost response is not automatically resubmitted, avoiding duplicate charges. Provider artifacts follow its retention policy; cancelling a local job does not cancel the remote batch. Separate bot runs are independent: avoid schedules that overlap pending batches on the same content.

## Endpoint checks

- Saving an enabled endpoint or its bot queues a synthetic inference through RQ; Core startup checks enabled saved endpoints, including unused ones. Disabled endpoints report `disabled`, clear their probe state, and skip queued stale probes/results. They do not degrade aggregate health; no enabled endpoints reports `n/a`. Checks exercise every enabled API format and its model (including a synthetic choice question for Decisions) and report healthy only when all succeed. The job budget allows 180 seconds per format. Checks exercise authentication, contain no story content, and may incur provider usage.
- Batch probes use the same asynchronous submit/retrieve flow. All enabled formats start before returning a pending retry. Completed per-format results persist in the job metadata, so subsequent retries neither repeat realtime inference nor poll a completed batch past its retrieval deadline. Final success or failure clears that probe state. Health stays pending until every synthetic inference completes; submission acceptance alone does not establish health.
- Failed checks retry after 10, 30, 120, and 300 seconds, subject to worker scheduling. After exhaustion, save the endpoint/bot or restart Core to recheck.
- Redis stores health separately from execution history. Each `check_id` identifies one scheduled check; saves/restarts replace it so delayed results are ignored. The configuration fingerprint also rejects results for changed settings. Deletion clears state. Worker configuration responses are non-cacheable; public status contains no credentials or provider error text.
- Pending/failed saved endpoints make `/health` return 503 with `worker_endpoints=down`; queues disabled means `n/a`. Container health tolerates endpoint-only degradation so administrators can repair configuration. Aggregate health and failure filters read each endpoint once rather than once per bot.
- Bot overview status prioritizes disabled, then failed/pending endpoint health, then last execution. Failed probes contribute to failure filters/menu counts; healthy probes clear only that failure. Completion invalidates settings, bots, menu badges, dashboard, and health caches.

## Entry Points and Coverage

- Validation: `src/models/models/llm.py`; persistence/resolution: `src/core/core/model/settings.py`; startup: `core/managers/db_seed_manager.py`.
- Boundaries: Core `api/settings.py`, `api/worker.py`; frontend settings view and `settings/llm.html`; worker `llm.py`, `llm_batch.py`, and the five LLM bots.
- Health: Core `service/endpoint_health.py`, worker `endpoint_health.py`, `/worker/endpoint-health/<kind>/<id>`.
- Coverage: Core settings/admin API and health lifecycle workflows; Chat client suite; worker bot and endpoint-check workflows; frontend admin settings and full-stack RQ tests. Extend these workflows rather than adding duplicate orchestration tests.
- The existing sentiment workflow in `tests/bots/test_bots.py` covers the complete request list, batch submission versus individual calls, unordered result correlation, and staged updates with frozen revisions only after completion. The pipeline workflow in `tests/bots/test_bot_tasks.py` covers mixed realtime/batch stages, checkpoint reloads, grouping before summary, and one final submission. `tests/unit/test_endpoint_health.py` covers combined-format probes, failure aggregation, per-format models, and asynchronous batch probes alongside realtime Decisions. The settings browser workflow covers enabling multiple formats, persisted models/URL overrides, and rejecting removal of an assigned format. Existing bot tests exercise prompts, parsing, and staged updates in immediate mode. These checks do not establish live provider model quality or availability.
