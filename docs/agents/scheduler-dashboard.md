# Scheduler Dashboard

Load for: `/admin/scheduler`, RQ registries, scheduled/active/failed jobs, execution history, or source/bot failure badges.

## Contracts

- Initial render loads queue/worker status and only the selected tab. All tab routes use one view and replace `#scheduler-content`, including its server-selected tab links; direct links render the full dashboard. No hidden panels or placeholder tables are retained.
- Payload-free `scheduler.changed` events from the shared SSE transport refresh queue cards and only the selected table, including Worker Summary. Initial connection and reconnect resync refresh authoritative state. There is no timer; an explained Refresh control appears only while realtime is disabled, connecting, or disconnected.
- Switching tabs resets search/page/limit/order/status; table navigation retains the selected tab. The shared `macros/live_table.html` controller keeps the request owner outside table swaps, throttles events to 300 ms with a trailing refresh, and resolves the latest query when a refresh starts. Navigation tracking holds the final event until the current navigation finishes, including when an earlier request was aborted. User navigation replaces pending requests, preventing old responses from overwriting a new tab or filter. Malformed/non-positive page/limit falls back to defaults.
- Core filters/orders/pages RQ lists after collecting registry entries; they are not SQL-backed. Endpoints always return paginated `items`/`total_count`. Frontend scheduler reads bypass list/detail caches so each event sees current state; task transition notices do not scan or invalidate frontend caches.
- Live job reads use one Redis pipeline; pending-job history is fetched in bulk. Completion checks load only job IDs and timestamps. Jobs removed from the scheduled registry during a read are skipped without failing the list.
- Queue Failures batches job reads per queue with `Job.fetch_many`; if a batch cannot be decoded, individual reads preserve valid rows and stale-entry cleanup.
- Cron history uses one bulk SQL query per source/bot family, ranking the latest matching result per schedule by last-run, last-success, then job ID. Matching preserves legacy exact IDs and cron prefixes with the task-name constraint; manual bot runs are excluded. History without worker identity still matches.
- Scheduled Jobs includes immediate queued jobs, deferred dependencies, and delayed jobs alongside configured cron jobs. Active reads running executions; both views check current RQ status and suppress entries whose terminal outcome has already been saved. Story bot names identify their action and story ID.
- Schedule counts include unique configured cron jobs, immediate queue entries, deferred/delayed registry jobs, and housekeeping without fetching/annotating full rows. Admin Dashboard count must match the full Scheduled Jobs dataset.
- Completed Runs retains the public action/story name from worker submissions; older history without names falls back to its worker label.
- Completed Runs lists persisted terminal results across users and background jobs, including committed pipeline steps, newest first. `/api/tasks/runs` uses the scheduler read permission, validates outcome/search/sort/paging, caps page size at 100 while returning the full matching count, omits private result data, and replaces historical failure text with curated reason messages. The frontend `/admin/scheduler/completed` supports direct links, HTMX, outcome filtering, pagination, and SSE refresh while preserving its query. It is independent of Redis result expiry.
- Active Jobs observes displayed executions by job ID and start time within the current table context. Event/reconnect/manual refresh sends observations in a CSRF-protected POST body; GET navigation resets observations. Unresolved executions remain observed when rows temporarily disappear. Pydantic parses the request and UTC-aware RQ start timestamps; the TaskRun model marks persisted result timestamps as UTC. Saved terminal timestamps must be at or after the observed start; row disappearance alone never means completion.
- Active rows mark endpoint probes with `tracks_completion=false` because probe health has no completed-run record. Only history-producing jobs are observed. The browser retains the newest 500 unresolved observations and 500 announced executions; discarded observations never count as completions. The POST rejects more than 500 observations. Navigation resets tracking as above.
- Refreshes and navigation replace `#scheduler-content`; the completion tracker and notice live outside it so the notice survives those swaps.
- Confirmed completions accumulate in one persistent blue notice without switching tabs. Dismissal clears its count; the link opens all Completed Runs with default filters. The notice survives Scheduler tab/query navigation, while observations reset. Leaving Scheduler clears local tracking. Each newly announced batch is recorded once in the tab-session Notification Center.
- `/api/tasks/runs` accepts repeated exact `job_ids` filters before counting/pagination. Omitted IDs retain the ordinary list; an explicitly empty ID matches nothing. Completion checks use uncached batches of 50 independently of table filters. Lookup failures retain observations and do not announce completion; SSE hints remain content-free.
- Active Jobs requires `CONFIG_WORKER_ACCESS`; Completed Runs separately requires `CONFIG_OSINT_SOURCE_ACCESS`. A forbidden completion lookup leaves the Active Jobs refresh working without announcing completions. Direct Completed Runs requests and denied live worker reads still return 403.
- Worker Summary (the history tab) statistics arrive as an aggregate mapping, filtered/ordered/paged in frontend; totals/statistics describe the full matching dataset.
- History and dashboard task totals count `WARNING` separately from successes and failures. Warnings contribute to total outcomes but not the full-success percentage; a warning-only/mixed-success group shows a yellow warning badge instead of All Success. Warnings still update last-success tracking because collection completed without failing.
- Source/Bot badges use latest persisted results for configured workers, not transient Queue Failures. Select latest statuses in SQL before counting/paging; exclude one-off `simple_web_collector` fetches. Failure filters preserve other query settings and reset pagination.
- Associate status by `Task.worker_id` and task family, never job-ID patterns. Source failure queries rank results per worker by last-run, last-success, then job-ID descending. Task writers must populate worker identity; scheduled-job history still uses job IDs.
- Sidebar views share one badge response per request, even without frontend caching. Missing/error results give zero badges; authorization failures propagate.
- Admin sidebar submenus show source/bot error counts on their summaries even when collapsed; destination badges retain their failure-filter links. The current destination's group opens on full navigation, including create/edit pages.
- Format UTC in the profile timezone. Queue Failures exposes only safe reason, enqueued budget, attempts, checkpoint progress/exhaustion, and job ID for log correlation; legacy jobs explicitly lack checkpoints. Encode diagnostics with Jinja JSON and render with `textContent`.
- `QUEUE_ENABLED=false` explicitly skips Redis initialization and startup scheduling. Enabled queues check Redis readiness up to five times, waiting 1, 2, 3, and 4 seconds between transient connection/timeout failures (including Redis loading); exhaustion fails startup. Authentication, authorization, and configuration errors fail immediately. Disabled broker/worker health is `n/a`, queue actions return 503, and cache invalidation requires an explicit `CACHE_REDIS_URL` to remain active. Independent worker/cron processes must be stopped separately.
- Core queue/cache and frontend cache Redis clients use redis-py's default RESP3 with `MaintNotificationsConfig(enabled=False)`. Worker/cron connections explicitly use RESP2 as well: RQ drops maintenance settings when rebuilding scheduler and spawned-worker connections, but preserves the protocol. This prevents unsupported maintenance-notification probes on Redis Open Source and leaves managed Redis Smart Client Handoffs unused.
- `src/models/models/scheduler.py` owns query defaults, UTC normalization, and serialization. Load diagnostic reason allowlists in one query. Never expose RQ exceptions, arbitrary historical messages, result data, provider bodies, or private checkpoints; malformed/missing results fall back to a worker-log reference.
- Core owns `rq:cron:def`: startup treats current source/bot/housekeeping specs as an allowlist and removes other persisted definitions and artifacts.
- Bulk cron reconciliation and source/bot registration loops batch task notices once per audience, including partial success before an error. Single-item changes still publish immediately.
- Cron rebuilds empty Redis through authenticated Core recovery without clearing newly queued work; pending jobs are disposable. See [Redis Runtime State](redis-runtime-state.md).

Bot failure filters and menu counts also include failed endpoint probes; execution history remains independent. See [LLM Endpoints](llm-endpoints.md#endpoint-checks).
