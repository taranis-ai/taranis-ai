# Asset SBOM Import

## When To Load

Asset SBOM uploads, software inventory, CPE coverage, import confirmation, component triggers, imported findings, replacement, Dependency-Track integration, or asset intelligence matching.

## Contracts

- The worker consumes CycloneDX JSON 1.5–1.7. Validation covers the inventory fields used by the importer, not the entire CycloneDX schema. Require at least one syntactically valid CPE on software; accept formatted CPE 2.3 and CPE URI names. No external lookup verifies product identity.
- Import one application/system asset. Exclude `file` components while still traversing their children. A file-type metadata root is the scan target, not an excluded inventory record. Include non-file metadata components.
- Group software by canonical package URL, component type, and version. Without a package URL, require matching type, namespace/group, name, version, suppliers, and CPEs. Retain each original component reference and Syft installation path. Never collapse solely by display name.
- Read CPEs from both `cpe` and Syft `syft:cpe23` properties. Preserve invalid values for preview warnings; persist valid values in component inventory and a deduplicated asset-level CPE projection for existing report associations. CPE-free software remains in inventory and receives the same product-name matching defaults as other components.
- Upload returns private `SbomUploadStatus` (`202` while queued/processing, `200` for an identical ready import). Core stages source bytes in `asset_sbom_upload`, queues a user-attributed `sbom_import_task` in `misc`, and exposes `/assets/sbom-uploads/{id}` for progress. The worker downloads the source through an API-key endpoint and runs `models/sbom_parser.py`; Core never parses the source JSON. It persists normalized batches of at most 100 components/findings, using a temporary reference index, and exposes the preview only after all expected batches finish. Queue arguments contain only the upload ID; no shared filesystem is required. Confirmation and asset replacement remain Core transactions.
- Worker callbacks recheck the uploader's current permission, organization and target access. Repeated accepted batches are idempotent. RQ failures discard partial previews; original bytes and temporary references are removed on success or failure. Stalled processing (one hour) and queued uploads (24 hours) expire on status reads and daily task-history cleanup. Ready previews retain their existing lifetime. Failed jobs can be retried by uploading again. Frontend progress polls every two seconds with a native refresh fallback, then navigates to the existing preview; failures stop polling.
- Upload and preview require `ASSETS_CREATE`; drafts belong to their importing user and organization. Confirmation rechecks destination group access, locks the import, and atomically creates the asset. Repeated confirmation returns the existing asset. The same user's repeated identical upload resumes its accessible import. For replacement, pass the target asset ID when uploading or reading the preview, then apply it with `PUT /assets/{asset_id}/sbom` and `{import_id, expected_sha256}`. A null expected hash means the asset has no inventory yet. Identical files already applied to another asset do not prevent an explicitly targeted update.
- Previews have no time limit and are not removed by later uploads. Only the latest confirmed snapshot remains with the asset; replacement removes the preceding snapshot and its obsolete associations. Deleting the asset cascades its inventory and findings. Inventory reads require `ASSETS_ACCESS` and current asset-group access. Import provenance records uploader, organization, filename, SHA-256, upload/confirmation times, document serial/version, generation time, exporter tools, subject description, and external references. After preparation, original file bytes are not retained.
- Core, frontend, and bundled production/development Nginx default to a 250 MiB request limit (including multipart overhead). The upload page reads the frontend limit from configuration. Keep all three layers aligned when overriding the limit. The parser bounds component count and nesting, and inventory responses paginate at 50 grouped components. The representative external Syft sample is roughly 46 MiB with about 78,000 component records, predominantly files; do not commit that full host inventory.

## Asset Classification Tags and Names

- Assets retain one destination group for organization access. Classification tags are independent, asset-owned labels in `asset_tag`, unique per asset/name and deleted with their asset. They never grant access and are separate from news-item/CVE tags.
- Asset responses and create/update inputs expose `tags: list[str]`; trim, lowercase and deduplicate names, ignoring blank entries. Omission preserves assignments on update; an empty list clears them. The asset form and new-asset SBOM confirmation accept one manually entered tag per line. SBOM replacement preserves tags and the asset name.
- Assets and Intelligence overview accept an exact normalized `tag` filter combined with other filters before pagination/aggregation. `/assets/tags` and the overview's `tags` choices include only labels on currently accessible assets; the tag catalog is read without frontend caching. Normal asset writes invalidate the asset cache.
- New-import previews suggest the suffix after the first whitespace-surrounded `/` when both sides are nonempty, trimming Unicode whitespace and preserving subsequent slashes. The suggestion stays editable; `summary.source_name` retains the original name. The prefix never supplies a destination group or tags. Parser version 3 stores both source and suggested names; older files are reparsed when uploaded again.
- Dependency-Track tag transfer remains deferred. Current downloaded CycloneDX 1.5 files omit project tags, so analysts enter them manually. This importer has no Dependency-Track-specific path.

## Triggers and Intelligence

- Bulk trigger selection applies only to the current filtered page. Submitting a selected rule still updates every package version in its review group.
- Intelligence responses paginate complete stories and contain `articles` keyed by news-item ID, not titles. Each article summarizes software using the same package identity as trigger review and distinct installed versions. Evidence shares exact `(field, excerpt)` pairs while retaining each matching phrase, actual context, and trigger/component/version association. Story software counts deduplicate packages across its visible articles. Current visibility and rule checks happen before grouping; stored matches remain per trigger/article, with no migration or rescan required for this presentation.
- Intelligence cards show article links and software/version counts; **Why this matches** opens the installed components and evidence. A single article sharing its story's title uses **Open article** to avoid repeating the heading. Alpine keeps only article expansion state outside the refreshed results section. Both scan polling and **Refresh results** replace the evidence, so preserving expansion never preserves stale content or permission decisions.
- Both intelligence views share match filters and evidence cards. `cve_match=yes` requires CVE evidence and retains software evidence when present; combine with `package_match=no` for strictly CVE-only results. Software and installed-component badges distinguish phrase evidence, CVE evidence and both. The same package can have different reasons across installed versions.
- Preview includes suggestions derived from component names, suppliers and CPE products/vendors. Confirmation saves them with their component and provenance (`sbom`, `cpe`, `supplier`). Specific component names, package names derived from PURLs, and CPE product names start enabled. Vendor-only and supplier terms stay disabled, unless the same phrase also identifies a product. Names shorter than three characters, non-alphabetic names, and the small `AMBIGUOUS_PRODUCT_NAMES` set stay disabled. External enrichment is outside the PoC. Analysts can optionally add aliases (`analyst`), edit phrases/context, and enable or disable rules. Generation only fills missing suggestions using their original key, preserving reviewed, edited and disabled rules.
- Review groups identical rules across versions of the same package. PURL ecosystem/namespace/name define the package identity; without a PURL, type/group/name/suppliers define it. Previously divergent phrase/context/enabled decisions remain separate groups. An edit or selection applies to every component in the displayed group; aliases are added across the package versions. Evidence retains each installed component/version. No schema migration or rewrite of existing analyst decisions is performed.
- Matching uses literal case-insensitive phrases with Unicode word boundaries and flexible whitespace. Context is an OR list: at least one context phrase must occur in the same article's title or content. The Python `requests` suggestion starts with `Python` context. Installed versions remain part of component identity but are not mandatory matching terms. HTML attributes and script/style text are not article evidence.
- Collection creates/replaces evidence in Core's ingestion transaction. Story and article edits also refresh it. Matches retain article IDs, trigger/component associations, the literal matching text, field and excerpt. The asset intelligence view groups by current story membership; grouping/ungrouping does not detach evidence. Mentions never create vulnerability findings or change the existing report-based vulnerability count.
- Import confirmation automatically starts an RQ `misc` job (`asset_match_task`) for articles collected in the last 30 days when the importer also has `ASSETS_ACCESS` and `ASSESS_ACCESS`. Confirmation retries return the same asset without queuing again. A queue failure leaves the asset and a failed run available for retry. Manual scans can change the lookback; 0 means all history. Core processes 200 articles per batch up to the scan's start time, persists a UUID cursor, and rechecks the requesting user's permissions and visibility on each batch. Progress is shown only to the initiating user. Confirmation opens Relevant intelligence (inventory for users without Assess access); its results section refreshes every two seconds while the latest run is queued/running and stops refreshing when the run finishes. The scan form stays outside the refreshed section. Read scan status before evidence so a completed status cannot stop polling with pre-completion results. A failed run can be replaced by a new scan. A worker killed before reporting failure can leave a run pending; restart the scan in that case.
- Trigger edits remove that trigger's old evidence; disabling removes its matches immediately. Re-enabling affects future collection; scan history after rule changes. Evidence reads recheck current text/context, source ACLs, canonical `Story.visible_query`, and individual article TLP to suppress stale or inaccessible results. Matching is potential relevance, not proof that the installed version is vulnerable.
- Reads require `ASSETS_ACCESS` and current asset-group access; intelligence/status also require `ASSESS_ACCESS`. Trigger writes use `ASSETS_CREATE`; historical scans also require `ASSESS_ACCESS`. API-key batch endpoints cannot elevate the initiating user's scope. Frontend calls bypass caches deliberately so permissions and reviewed rule/evidence state are current. Review groups paginate at 50 and intelligence at 20 stories.
- Deleting an asset cascades inventory, imported findings, triggers, matches, and historical runs.

## Cross-host Intelligence Overview

- Assess's optional `asset_match=true` filter reuses the overview's accessible assets and `matching_stories` current-evidence checks, without overview-specific filters or a new scan. The matcher accepts Assess's filtered/sorted story query; `assess_match_page` accumulates counts in bounded batches and returns all matching asset names for the selected page. See [Assess Filters](assess-filters.md) for cache and navigation behavior.
- Individual asset intelligence delegates to the same overview filtering service, pins the path asset ID, and returns its article evidence directly. Filters survive navigation between the views, pagination, refresh and scan redirects. When opened from Assess, both intelligence views retain a local Assess return URL and show Back to Assess; this context stays in the frontend and survives filtering and clearing intelligence filters.
- **Assets → Intelligence overview** (`GET /assets/intelligence` in Core and frontend) groups current results by story → news-item ID → host. The same article appears once, including when it matches several hosts. Each host retains its own software, installed versions and evidence. Article CVE badges count distinct CVE IDs across the filtered hosts, not source records or installations.
- `cve_match`, `package_match`, and `cvss_available` accept `any`, `yes`, or `no`. `asset_id`, `group_id`, and literal case-insensitive `package` (name or PURL) narrow the scope. All filters apply to the same article/host association after package selection. CVE evidence on another host, unrelated findings, and ratings for other packages cannot satisfy them. Requiring both match types does not require the same component; the UI explains the article/host scope.
- `cve_id` requires an exact normalized CVE association and restricts its CVE evidence and ratings. `collected_from`/`collected_to` filter both matching paths by inclusive article collection instants. Core accepts UTC or explicit-offset timestamps and normalizes to UTC. Frontend date inputs cover complete calendar days using existing `select_timezone()` profile/config fallback, with each boundary’s daylight-saving offset; links and inputs retain local dates. These filters are independent of scan lookback.
- `cvss_min` and `cvss_max` are inclusive bounds on the highest valid reported CVSS score for that association, across sources and CVSS versions. Availability means at least one numeric score for a matching CVE/component; zero is a score, absent is unknown. Accept CVSSv2/v3/v31/v4 methods, or explicit CVSS 3.0/3.1/4.0 vector prefixes when the method is absent. Ignore non-CVSS, nonfinite, out-of-range or unassociated ratings. Keep each score's source (rating source, falling back to finding source), vector and exact source-record component references. Package selection must not borrow ratings from another source record for the same CVE.
- `matching_stories` supplies the shared, bounded candidate/evidence reads for individual assets and the overview. Recheck story visibility, source ACLs, article TLP and current matching decisions before filtering, counting and paginating complete stories (`limit` 1–100, default 20). Totals count all matching visible stories and distinct articles, once per article regardless of host count. Counting streams candidate batches and retains only the requested result page. Host/group choices follow individual asset access: the user's organization plus the shared default group. No cross-organization names, counts or associations are exposed.
- Native filter submissions reset the page; pagination and HTMX refresh retain filters. Both views use the existing `CacheObject` pagination metadata and `macros/table.html::table_controls`; results report total stories/articles and the current story range/article count. A story may contain multiple articles, so article counts may exceed the story page size. Expansion state is keyed by article and host, outside the replaced results section. Existing matches work without reimporting or rescanning; scores are read from retained source records, with no external lookup or new tables.
- Entry points: `core/service/asset_intelligence_overview.py`, `service/asset_findings.py::finding_cvss_ratings`, `models/asset_intelligence.py::IntelligenceFilters`, frontend `assets/intelligence_overview.html` and the shared `assets/article_matches.html`. Core's SBOM workflow covers host isolation, package/source-specific scores, unknown versus zero scores, bounds, live decisions, access, date/CVE combinations, count deduplication and pagination. Frontend request coverage checks local-date conversion across daylight-saving transitions; the browser workflow checks filter-preserving host navigation. The recorded findings workflow imports a second host and demonstrates overview discovery, deduplication, score/package filtering, refresh and article navigation.

## Imported Findings and Replacement

- `models/sbom_parser.py::parse_sbom` normalizes inventory and findings without persistence. `service/sbom_upload.py` owns preparation state and batched persistence; `service/asset_sbom.py` owns comparison and transactional application; API and upload views are adapters. Calling `stage_upload`, `compare_import`, and `apply_import` requires no interactive UI. `apply_import` commits atomically; schedule the historical scan only afterward. Access and destination scope are rechecked on application.
- Retain source vulnerability records, including IDs, sources, descriptions, ratings/vectors, CWEs, dates, analysis, and `affects` version details. Normalize CVE identity with the existing IOC normalization. Multiple records for a CVE share one finding and matching decision. Non-CVE identifiers remain available in CTI without CVE matching. Associate only exact declared references to retained software; unknown, file-only, or absent references are unresolved, never inferred from names or synthetic occurrence labels.
- New `asset_sbom_finding` and `asset_sbom_finding_component` tables use metadata initialization. They do not create `AssetVulnerability` report links or increase the report vulnerability count. Import provenance and original records are separate from cached IOC enrichment. UI labels findings as source-reported assessments, not confirmed exposure.
- Preview shows distinct findings/CVEs, affected components, unresolved references, and component/finding/CVE additions and removals when targeting an asset. A missing `vulnerabilities` section warns before clearing previous imported findings; an explicitly empty array reports zero supplied findings. Parser revision in summary JSON lets the same file upgrade an earlier inventory-only import despite an identical SHA-256.
- Replacement locks the asset and preview, rejects a mismatched expected SHA-256 with 409, and preserves asset identity/group, name, description, serial, manual observables, and CPEs outside the previous SBOM projection. Retrying the applied preview does not queue another scan. Stale or inaccessible previews cannot replace the current snapshot.
- Exact installed-version rules move to the replacement components, retaining rule IDs and valid evidence. New versions inherit package-wide decisions only where all previous versions agree. Conflicting inheritance stays disabled and marked for review; editing or explicitly enabling/disabling the rule clears that marker. CVE decisions survive by normalized ID. Removed components lose their rules/evidence. Queued/running product scans become `SUPERSEDED`; Core batches and workers treat this as terminal. Replacement starts the usual 30-day scan after commit when authorized.
- IOC Bot remains the CVE extractor. Live joins between current findings and existing CVE/cves news-item tags determine relevance; there is no CVE/article evidence table or external lookup. CVE matching defaults on, is independent of product-name triggers, and applies across all source records of a CVE through `PUT /assets/{asset_id}/sbom/cves/{cve_id}`. Disabling retains the finding in CTI. Removing tags/findings or access updates intelligence on the next read without rescanning. A tag is evidence in its own right; no textual excerpt is invented.
- Product and CVE matches share one article card and software summary. Candidate stories are read in bounded batches; visibility, article TLP and current product evidence are checked before story pagination. CVE matching covers existing tagged history, independent of the product scan lookback.
- Asset CTI and its overview paginate 50 distinct indicator/finding IDs, accepting `page` and `search` (CVE ID, component name or PURL). Results include source records, exact reference-to-installed-component mappings, unresolved references, and cached enrichment. Findings remain visible when matching is disabled; inaccessible articles never appear in associations. Story/report CTI response contracts are unchanged.

## Future Dependency-Track Connector Contract (Deferred)

The connector itself is not implemented. Its agreed identity is **one Dependency-Track project UUID per Taranis asset**, even when different project UUIDs represent releases of the same product.

1. Configure connection/API credentials, destination organization/group and schedule once. Enumerate every project visible to that API key with pagination and fetch vulnerability-inclusive CycloneDX exports, even when inventory has not changed.
2. Persist a unique `(organization, source connection, project UUID) → asset ID` mapping. Names are display metadata, never identity. Existing manually uploaded assets require one explicit source mapping; later create/update decisions are automatic.
3. Use the shared parser and transactional application service: create unmapped projects, update changed mapped projects, skip unchanged normalized inventory **and findings**. Ignore export timestamps and regenerated document/component references when comparing; preserve reference associations while canonicalizing. Raw upload SHA-256 protects manual updates but is not the future semantic-change fingerprint.
4. Add database uniqueness and per-project synchronization state with safe retries/overlap. Keep the last successful snapshot on invalid, inaccessible or disappeared projects; never automatically delete assets. Record per-project status and curated errors. A connector must enforce its configured organization/group scope and queue matching only after successful application.

Dependency graphs, licenses, snapshot history and automatic external enrichment remain deferred.

## Local PoC Walkthrough

1. Open **Assets → Import SBOM**, select a CycloneDX JSON file, and preview component/CPE coverage and automatic matching terms.
2. Confirm the host/application name and destination group, then create the asset. **Relevant intelligence** opens and automatically shows matches when the initial scan completes.
3. Use **CVE matches only** to focus on tagged vulnerability matches; each article's badge counts its distinct matching CVEs. Expand **Why this matches** to inspect installed versions, CVE associations and shared excerpts, or follow an article link to Assess. New or changed collected articles are matched automatically.
4. Open **CTI information** to search imported CVEs or components, expand source assessments and installed versions, and control CVE matching independently. Use **SBOM inventory → Update SBOM** to review and apply a replacement.
5. Optionally open **Component triggers** to refine noisy matches. Use **Edit trigger** to change an existing matching phrase or its context phrases; use **Add alternative matching phrase** for an additional rule. One review decision covers the listed package versions. Use **Scan existing articles** after changing rules or to search a longer period.
6. Open **Assets → Intelligence overview** to compare all accessible hosts. Combine CVE, package-name and score-availability choices with a CVSS range, host/group selection or package search. Expand a host's **Why this matches** to see exact installed components and rating provenance.

The scan needs a running worker subscribed to `misc`. Restart Core after applying the feature so metadata creates the new tables; restart the frontend and worker to load their changes. Follow the developer's chosen local startup workflow. No external scanner or enrichment service is needed.
