# Asset SBOM Import

## When To Load

Asset SBOM uploads, software inventory, CPE coverage, import confirmation, component triggers, imported findings, replacement, Dependency-Track integration, or asset intelligence matching.

## Contracts

- The worker consumes CycloneDX JSON 1.5–1.7. Validation covers the inventory fields used by the importer, not the entire CycloneDX schema. Require at least one syntactically valid CPE on software; accept formatted CPE 2.3 and CPE URI names. No external lookup verifies product identity.
- Import one application/system asset. Exclude `file` components while still traversing their children. A file-type metadata root is the scan target, not an excluded inventory record. Include non-file metadata components.
- Group software by canonical package URL, component type, and version. Without a package URL, require matching type, namespace/group, name, version, suppliers, and CPEs. Retain each original component reference and Syft installation path. Never collapse solely by display name.
- Read CPEs from both `cpe` and Syft `syft:cpe23` properties. Preserve invalid values for preview warnings; persist valid values in component inventory and a deduplicated asset-level CPE projection for existing report associations. CPE-free software remains in inventory and receives the same product-name matching defaults as other components.
- Upload returns private `SbomUploadStatus` (`202` while queued/processing, `200` for an identical ready import). Core stages source bytes in `asset_sbom_upload`, queues a user-attributed `sbom_import_task` in `misc`, and exposes `/assets/sbom-uploads/{id}` for progress. The worker downloads the source through an API-key endpoint and runs `models/sbom_parser.py`; Core never parses the source JSON. It persists normalized batches of at most 100 components/findings, using a temporary reference index, and exposes the preview only after all expected batches finish. Queue arguments contain only the upload ID; no shared filesystem is required. Confirmation and asset replacement remain Core transactions.
- Worker callbacks recheck the uploader's current permission, organization and target access. Repeated accepted batches are idempotent. RQ failures discard partial previews; original bytes and temporary references are removed on success or failure. Stalled processing (one hour) and queued uploads (24 hours) expire on status reads and daily task-history cleanup. Ready previews retain their existing lifetime. Failed jobs can be retried by uploading again. Frontend progress polls every two seconds with a native refresh fallback, then navigates to the existing preview; failures stop polling.
- Upload and preview require `ASSETS_CREATE`; drafts belong to their importing user and organization. Confirmation rechecks destination group access, locks the import, and atomically creates the asset. Repeated confirmation returns the existing asset. The same user's repeated identical upload resumes its accessible import. For replacement, pass the target asset ID when uploading or reading the preview, then apply it with `PUT /assets/{asset_id}/sbom` and `{import_id, expected_sha256}`. A null expected hash means the asset has no inventory yet. Identical files already applied to another asset do not prevent an explicitly targeted update.
- Previews have no time limit and are not removed by later uploads. Only the latest confirmed snapshot remains with the asset; replacement removes the preceding snapshot and its obsolete associations. Deleting the asset cascades its inventory and findings. Inventory reads require `ASSETS_ACCESS` and current asset-group access. Import provenance records uploader, organization, filename, SHA-256, upload/confirmation times, document serial/version, generation time, exporter tools, subject description, and external references. After preparation, original file bytes are not retained.
- Core, frontend, and bundled production/development Nginx default to a 250 MiB request limit (including multipart overhead). The upload page reads the frontend limit from configuration. Keep all three layers aligned when overriding the limit. The parser bounds component count and nesting, and inventory responses paginate at 50 grouped components. The representative external Syft sample is roughly 46 MiB with about 78,000 component records, predominantly files; do not commit that full host inventory.

## Asset Classification Tags and Names

- Assets retain one destination group for organization access. Classification tags are independent, asset-owned labels in `asset_tag`, unique per asset/name and deleted with their asset. They never grant access and are separate from news-item/CVE tags.
- Asset responses and create/update inputs expose `tags: list[str]`; trim, lowercase and deduplicate names, ignoring blank entries. Omission preserves assignments on update; an empty list clears them. The asset form and new-asset SBOM confirmation accept one manually entered tag per line. SBOM replacement preserves tags and the asset name.
- Assets accepts exact normalized `tag`; Assess uses `asset_tag`, combined with its other matching criteria. `/assets/tags` and `/assess/asset-filter-lists` include only labels on currently accessible assets; the tag catalog is read without frontend caching. Normal asset writes invalidate the asset cache.
- New-import previews suggest the suffix after the first whitespace-surrounded `/` when both sides are nonempty, trimming Unicode whitespace and preserving subsequent slashes. The suggestion stays editable; `summary.source_name` retains the original name. The prefix never supplies a destination group or tags. Parser version 3 stores both source and suggested names; older files are reparsed when uploaded again.
- Dependency-Track tag transfer remains deferred. Current downloaded CycloneDX 1.5 files omit project tags, so analysts enter them manually. This importer has no Dependency-Track-specific path.

## Shared Software Rules and Assess Matching

- Assess is the sole matching-story and article-evidence workspace. Assets retains details, software inventory, Matching rules, Findings & indicators and SBOM management. The superseded single-asset/cross-asset intelligence list routes, APIs, filters and templates are removed; there are no compatibility wrappers. Assess cards show compact asset summaries with source-reported severity and matching CVE counts; detailed evidence loads on demand. See [Assess Filters](assess-filters.md) for exact qualification, CVE AND semantics, scores, access and paging.
- `SoftwareMatchRule` owns phrases, context and provenance per importing organization and package. Package identity ignores installed version: component type plus PURL ecosystem/namespace/name, or type/group/name/suppliers without a PURL. It never shares phrases across organizations, even for assets in the shared default group. The importing organization's users with `ASSETS_CREATE` can edit shared wording; `AssetTrigger` retains each installation's independent enabled/review choice.
- Imports reuse shared rules, including edited phrases and analyst aliases. Suggestions derive from SBOM names, PURLs, CPE product/vendor names and suppliers. Eligible product names default enabled; broad vendor/supplier and ambiguous names default disabled. Missing suggestions use their original phrase key so generation does not recreate edited rules. Adding an alias attaches it across existing installations of that package in the organization; other assets enable it only on components already participating in software matching. Later imports apply their own matching opt-in. Shared rules survive deletion of the last asset so future imports can reuse them.
- Review groups a shared rule across installed versions with the same enabled state. Editing applies wording to all installations sharing the rule and enabled state only to the displayed asset group. Bulk enable/disable applies only to selected groups on the current filtered page. Evidence retains each installation and version. Shared wording edits invalidate stored evidence across participating assets; disabled rules lose their matches immediately. Re-enabling affects future collection; rescan affected assets after changing shared wording.
- Literal case-insensitive phrases use Unicode word boundaries and flexible whitespace. Context is OR: at least one phrase must occur in the same article's title or content. Python `requests` starts with `Python` context. Installed versions are evidence, not mandatory search terms. HTML attributes and script/style text are excluded.
- Create/replacement confirmation accepts independent `enable_software_matching` and `enable_cve_matching`, defaulting true. Opting out retains suggestions/findings. Existing installation and CVE decisions survive replacement; these options seed new ones. Confirmation opens Assess scoped to the asset, or inventory without Assess access.
- Collection and article/story edits refresh software evidence in Core's transaction. Evidence stores article IDs, trigger/component links, matched text, field and excerpt. Story grouping retains article associations. CVE matches join current imported findings to exact normalized article tags without a scan. Neither path creates vulnerability findings or changes report-based vulnerability counts.
- Automatic historical scans use an RQ `misc` job (`asset_match_task`) for the last 30 collection days when the importer has Assess/Assets access and enabled software rules. Retries do not queue again. Manual controls and progress live in Matching rules; lookback 0 means all history. Core checks 200 articles per batch up to scan start, persists a cursor, and rechecks the initiating user's current scope. Status belongs to that user. Single-asset Assess polls while active, reading status before stories so completion includes final results. Queue failures leave the asset and a static failed status available for retry.
- Reads recheck current text/context, story/source ACLs, article TLP, asset-group access and enabled findings/rules. Assess matching/catalog/evidence require both access permissions; trigger writes require `ASSETS_CREATE`, scans additionally `ASSESS_ACCESS`. These frontend reads are uncached. Rule pages paginate at 50 groups. Matching indicates potential relevance, not confirmed vulnerability.
- Branch-only tables use metadata initialization, with no shipped database migration. Existing local development snapshots with the former per-asset rule layout require an explicit local schema repair or a fresh disposable database; automatic startup does not rewrite their decisions.

## Imported Findings and Replacement

- `models/sbom_parser.py::parse_sbom` normalizes inventory and findings without persistence. `service/sbom_upload.py` owns preparation state and batched persistence; `service/asset_sbom.py` owns comparison and transactional application; API and upload views are adapters. Calling `stage_upload`, `compare_import`, and `apply_import` requires no interactive UI. `apply_import` commits atomically; schedule the historical scan only afterward. Access and destination scope are rechecked on application.
- Retain source vulnerability records, including IDs, sources, descriptions, ratings/vectors, CWEs, dates, analysis, and `affects` version details. Normalize CVE identity with the existing IOC normalization. Multiple records for a CVE share one finding and matching decision. Non-CVE identifiers remain available in CTI without CVE matching. Associate only exact declared references to retained software; unknown, file-only, or absent references are unresolved, never inferred from names or synthetic occurrence labels.
- New `asset_sbom_finding` and `asset_sbom_finding_component` tables use metadata initialization. They do not create `AssetVulnerability` report links or increase the report vulnerability count. Import provenance and original records are separate from cached IOC enrichment. UI labels findings as source-reported assessments, not confirmed exposure.
- Preview shows distinct findings/CVEs, affected components, unresolved references, and component/finding/CVE additions and removals when targeting an asset. A missing `vulnerabilities` section warns before clearing previous imported findings; an explicitly empty array reports zero supplied findings. Parser revision in summary JSON lets the same file upgrade an earlier inventory-only import despite an identical SHA-256.
- Replacement locks the asset and preview, rejects a mismatched expected SHA-256 with 409, and preserves asset identity/group, name, description, serial, manual observables, and CPEs outside the previous SBOM projection. Retrying the applied preview does not queue another scan. Stale or inaccessible previews cannot replace the current snapshot.
- Within the importing organization, exact installed-version rules move to the replacement components, retaining rule IDs and valid evidence. New versions inherit package-wide decisions only where all previous versions agree. Conflicting inheritance stays disabled and marked for review; editing or explicitly enabling/disabling the rule clears that marker. CVE decisions survive by normalized ID, including when a different organization replaces a shared-default-group asset; software rules then come from the new importing organization. Removed components lose their rules/evidence. Queued/running product scans become `SUPERSEDED`; Core batches and workers treat this as terminal. Replacement starts the usual 30-day scan after commit when authorized and enabled software rules remain.
- IOC Bot remains the CVE extractor. Live joins between current findings and existing CVE/cves news-item tags determine relevance; there is no CVE/article evidence table or external lookup. CVE matching defaults on, is independent of product-name triggers, and applies across all source records of a CVE through `PUT /assets/{asset_id}/sbom/cves/{cve_id}`. Disabling retains the finding in CTI. Removing tags/findings or access updates intelligence on the next read without rescanning. A tag is evidence in its own right; no textual excerpt is invented.
- Product and CVE matches share one article card and software summary. Candidate stories are read in bounded batches; visibility, article TLP and current product evidence are checked before story pagination. CVE matching covers existing tagged history, independent of the product scan lookback.
- Asset CTI and its overview paginate 50 distinct indicator/finding IDs, accepting `page` and `search` (CVE ID, component name or PURL). Results include source records, exact reference-to-installed-component mappings, unresolved references, and cached enrichment. Findings remain visible when matching is disabled; inaccessible articles never appear in associations. Story/report CTI response contracts are unchanged.

## Future Dependency-Track Connector Contract (Deferred)

The connector itself is not implemented. Its agreed identity is **one Dependency-Track project UUID per Taranis asset**, even when different project UUIDs represent releases of the same product.

1. Configure connection/API credentials, destination organization/group and schedule once. Enumerate every project visible to that API key with pagination and fetch vulnerability-inclusive CycloneDX exports, even when inventory has not changed.
2. Persist a unique `(organization, source connection, project UUID) → asset ID` mapping. Names are display metadata, never identity. Existing manually uploaded assets require one explicit source mapping; later create/update decisions are automatic.
3. Use the shared parser and transactional application service: create unmapped projects, update changed mapped projects, skip unchanged normalized inventory **and findings**. Ignore export timestamps and regenerated document/component references when comparing; preserve reference associations while canonicalizing. Raw upload SHA-256 protects manual updates but is not the future semantic-change fingerprint.
4. Add database uniqueness and per-project synchronization state with safe retries/overlap. Keep the last successful snapshot on invalid, inaccessible or disappeared projects; never automatically delete assets. Record per-project status and curated errors. A connector must enforce its configured organization/group scope and queue matching only after successful application.

Dependency graphs, licenses, snapshot history and automatic external enrichment remain deferred.

## Local PoC Walkthrough

1. Open **Assets → Import SBOM**, preview the software and findings, then confirm the asset/group/tags and matching choices.
2. Scoped **Assess** opens; CVEs match existing tags immediately and scan progress refreshes software matches as they arrive. Use **Advanced asset filters** for scope, match types and CVSS bounds, and normal tag selection for specific CVEs.
3. Open **Why this matches** on a story to inspect article/asset evidence, source ratings and installed versions. Follow an asset to details, inventory or findings, then use **Back to Assess** to restore criteria and page.
4. In **Matching rules**, edit shared phrases/context once for the organization’s software, choose participation per asset, and scan existing articles. In **Findings & indicators**, control imported CVE matching independently.
5. Use **Software inventory → Update SBOM** to compare and replace the current snapshot. Confirmation returns to scoped Assess. **Assets → Matching stories in Assess** browses all accessible matching assets.

The scan needs a worker subscribed to `misc`. Follow the developer’s chosen startup workflow. No external scanner or enrichment service is required.
