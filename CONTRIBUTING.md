# Contributing

Keep contributions focused, explain the problem and your approach, and follow the
[development workflow](docs/agents/development-workflow.md) for setup, validation,
and feature signoff. Agents must also follow [AGENTS.md](AGENTS.md).

## Responsibility and review

You are responsible for every change you submit, whether it originated from an
LLM, the internet, another person, or another tool. Review and understand what
the code does and why it belongs in this project. Be prepared to explain your
decisions, answer review questions, and investigate answers you do not know.
Resolve anything you cannot explain or take responsibility for before requesting
review. You must have the necessary rights to contribute under the project's
license and preserve applicable third-party notices.

Opening a PR includes a commitment to follow through: address feedback,
investigate failures, and make necessary corrections. Do not leave maintainers
to discover and fix problems you have not investigated. Maintainers may close a
PR if a request for contributor action goes unanswered for seven calendar days.
If you need more time, communicate that; closure remains a maintainer decision.

## LLM assistance

LLM-assisted contributions are welcome and carry the same responsibilities as
any other contribution. Include the actual task prompt and follow-up prompts
that materially changed the implementation in the PR description, a PR comment,
or a linked issue. If they are elsewhere, link their location from the PR
description. Remove secrets and private information, clearly marking redactions.
Tool and model names are optional; they do not replace the prompts.

Do not add `Co-authored-by:`, `Assisted-by:`, `Generated by`, or similar attribution
for tools to commit messages. Tools are not project authors, and promotional
attribution provides no useful review context. This restriction does not prohibit
legitimate human co-author attribution or required third-party notices.

## Preparing a PR

Use the [PR template](.github/pull_request_template.md), including when opening a
PR through a CLI or API. Human contributors must complete the contributor
confirmations themselves or explicitly authorize an agent to record them.

Include a concise explanation of the change and actual validation results in
the description. Identify checks not run and explain why. For features, follow
the full signoff procedure in the development workflow. Highlight important
decisions, risks, and useful verification steps; include screenshots for UI
changes and migration or rollback notes where relevant. Human review-time
estimates are optional.

Keep the description, prompt disclosure, and validation evidence current when
review changes alter the implementation. Rerun applicable validation for the
updated changes; earlier results do not establish that the revised code passes.
